# Releasing locally

No GitHub Actions or App Store. Use this Mac with Xcode 27+, XcodeGen, the Apple team account in Xcode, a usable **Developer ID Application** certificate/private key for team `227GEZ2676`, and notarization credentials already stored as `mac-videos-notary`. Never put certificates, profiles, passwords or downloaded Google configuration in git. Unlock the login Keychain yourself and authorize codesign if macOS requests private-key access; do not send a password to an agent.

1. Work in a clean isolated worktree. Update `MARKETING_VERSION` and increment `CURRENT_PROJECT_VERSION` in project.yml (v1.0.0 starts at build 2), then run `xcodegen generate` and commit the spec and generated files.
2. Run `./scripts/check.sh`, review code/security, open the PR, record results and rerun checks on the exact final head before merge.
3. Run `./scripts/release.sh 1.0.0` (optional second argument overrides the build number; use a larger number for another build). The script archives a universal Intel/Apple silicon Release with hardened runtime, camera/microphone entitlements and data protection Keychain, exports Developer ID with an embedded distribution profile, tests only synthetic Keychain items, submits a ZIP using `notarytool --wait`, requires **Accepted**, staples the app and validates with stapler and Gatekeeper. It fails closed; inspect the retained local archive/export logs on failure.
4. Only after checks pass, merge the PR and make the release from that source commit. If main changed, rebuild from the merged source. Attach **mac-videos-VERSION-universal.zip** and **SHA256SUMS.txt** from `.build/releases/VERSION-BUILD/`. Never attach `submission.zip` (it predates stapling), archives, profiles or logs. Keep release artifacts outside git.
5. Publish using `PATH=/opt/homebrew/bin:/usr/local/bin:$PATH gh release create v1.0.0 --repo GolferGeek/mac-videos --target EXACT_MAIN_SHA --title 'mac-videos 1.0.0' --notes-file NOTES_FILE ZIP SHA256SUMS`. Announce only the functionality and limitations actually verified.
6. Download the published ZIP, verify SHA256SUMS, unzip, run `codesign --verify --deep --strict`, `xcrun stapler validate` and `spctl -a -vv --type execute` on the extracted app. Quit the installed app normally; if it refuses to quit because recording/upload is active, leave it and finish later. Preserve a backup outside the repo, install the downloaded app at `/Applications/mac-videos.app`, then launch and inspect it. Never force-quit a recording/upload or delete old Keychain items.

The script does not publish, install or modify any real Google setup. Build artifacts and Xcode-managed profiles stay local. Real capture/playback and Google sign-in/upload are separate integration checks that require the user's permissions/account.

## Why data protection Keychain

The signed-in Xcode account can now archive with a provisioning profile, and Developer ID export can request a distribution profile. Release enables `DATA_PROTECTION_KEYCHAIN` and the team-scoped `227GEZ2676.io.golfergeek.mac-videos` access group. The exported profile must authorize that group; an entitlement alone is insufficient. The synthetic exported-bundle test checks create/update/read across launches/delete and rejection of another identity before notarization.

Data protection storage is separate from earlier file-Keychain items, even where the service name matches. There is no automatic migration or legacy read: Matt pastes his existing Google setup and signs in once. This avoids password prompts from stale ACLs and leaves his old items untouched. Debug retains the prior signed-v2 file-Keychain mode. See [Apple's Mac keychain guidance](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains) and [notarization guidance](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).
