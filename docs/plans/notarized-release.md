# Notarized release plan

- Goal: publish v1.0.0 as a Developer ID signed, notarized and stapled download, install it in Applications and verify Gatekeeper accepts the exact download.
- Files: scripts/release.sh, release entitlements/export options, project.yml/generated project/Info.plist version metadata, README and user/release guides, Keychain mode selection if provisioning succeeds, synthetic Keychain check script, Matt queue and review evidence. Capture/session/window filters and existing credentials remain untouched.
- Approach: archive with Xcode, export Developer ID with automatic provisioning if available, notarize a ZIP, staple the app, then recreate the download ZIP. A provisioned data protection access group is preferred; use an isolated Developer ID file-Keychain namespace only if distribution provisioning fails. Never query or migrate old credential items. No App Store, shared Google client, remote CI or new runtime dependency.
- Risks: identity/storage transition requires pasting existing Google setup and signing in once. Permissions may need renewal by the user. Release signing, entitlements and credential isolation require security review. Publishing and merging are explicitly authorized by the brief.
- Tests: full check.sh before PR and on exact head before merge; archive/export signatures, embedded profile and entitlement inspection, signed synthetic Keychain create/read/update/delete and other-identity denial, notarization Accepted, stapler validation, spctl assessment, download round trip, native launch. Real Google upload/capture requires interactive account/permission evidence and must be reported honestly.
- Size: one focused release slice. No review-lessons catalog. All planning, implementation and reviewer roles performed directly in Codex per the handoff's explicit instruction; no subagents.
